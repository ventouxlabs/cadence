See `docs/architecture.md` §2.
- **D-009** · Cadence has no login of its own. It is reachable only over Tailscale (and optionally an NPM access list). Why: a login screen makes Today slower for a kid; the brief's security boundary is the homelab. Change: add a middleware reading `CADENCE_ACCESS_TOKEN` (PRP-09 documents how).
- **D-010** · Imported and AI-generated workouts live in the DB only (`source = import|generated`); the app never writes to `library/`. Why: removes path-traversal surface from `/api/import`; seed YAML stays reviewable in git.

- **D-013** · Together mode is two sessions linked by `together_group_id`, one Done. Why: write-back must stay per person and per Garmin-push setting.
- **D-014** · Codex CLI on this machine is signed in with a ChatGPT account, which rejects `gpt-5.1-codex` ("not supported when using Codex with a ChatGPT account"). Adversarial reviews use the CLI default model `gpt-5.6-terra` (probe returned OK); if that fails on a given PRP, a second independent Claude reviewer subagent runs the same brief and the PRP log says so.
- **D-015** · VitalForge holds one Garmin credential (the parent's). `POST /p/{slug}/api/activity` with `push_to_garmin: true` for a different person returns 409 **unless** the body also carries `garmin_target: "credential_person"`, in which case the activity is created under the parent's Garmin with the name prefixed by the person's display name (e.g. "Cadence (Son) — Lower A"). Cadence sends that field only when the `push_son_to_garmin` setting is on. Why: the brief wants opt-in pushing of the son's sessions to JD's account; the contract wants no silent misfiling. Both hold.
- **D-016** · Cadence's write-back retry is a bounded, client-driven re-POST of the same `session_id` (exponential backoff 1 min → 2 h, max 8 attempts, never on 409/422). Why: VitalForge has no retry worker and `garminconnect` has no 429 backoff; a tight loop could get the shared credential blocked and break weight logging too (contract §5.9).
- **D-017** · Person slugs default to `me` → `VITALFORGE_PERSON_ME` and `son` → `VITALFORGE_PERSON_SON` env vars (blank in `.env.example`); editable in Settings. Why: VitalForge persons are path slugs and Cadence cannot list them without admin.
- **D-018** · `UNKNOWN` is not a `garminconnect` 0.3.11 exercise category (contract §3.1). In the schema `garmin_category` is `Optional[str]` validated against the 26 confirmed names; wherever `docs/exercise-principles.md` says `UNKNOWN`, the seed YAML uses `null`, the activity payload omits the field, and VitalForge skips exercise-set upload for that exercise (the activity itself is still created).
- **D-019** · Adopted the principles doc's judgment calls verbatim: `load_unit` enum (`per_hand`/`per_implement`/`total`/`bodyweight`); kettlebells illegal under 14, two-handed 16 kg max for 14–17 with a 45.7 kg bodyweight gate, 24 kg adult-only; youth loaded rep floor 8; `has_overhead_anchor` profile boolean (dead hang records `unavailable`, never a gap, without it); `bench_assisted` legal under 10; illegal loads clamp down instead of rejecting a row at program-build time (the *validator* still rejects imported/generated docs that break caps); Done always tappable with a per-band promotion threshold; precedence rules P1–P7.

Why: PRP-00 §4.1's criterion is "confirmed present in `exercises.CATEGORIES`", and `docs/vitalforge-contract.md` §3.1 confirms `CARDIO` under its fallback list; the seed spec (`docs/exercise-principles.md` §9) maps three exercises to it, so omitting it would block PRP-01. `UNKNOWN` remains absent (D-018). Change: add or drop members in `cadence/schema/enums.py` only.
- **D-029** · `library/youth_rules.yaml` ships all four bands, not the `u10`-only fixture of PRP-00 §4.7. Why: the band table must match `docs/exercise-principles.md` §3 exactly, and principles has landed, so the risk that PRP-00 §9.4 guarded against (freezing numbers early) is gone; acceptance test 25 gains three bands of coverage instead of one. Change: PRP-01 edits the YAML, never the test.
- **D-030** · `validate_workout` fails closed on missing inputs. No `exercises` catalog makes every row `unknown_exercise`; no `youth_rules` table for a youth profile emits a new code, `youth_rules_unavailable`. Why: a gate that cannot perform its check must not report a pass. This adds one code to PRP-00 §5.1's table. Change: pass the catalog and the rule table, which every real caller already has.
- **D-031** · `validate_workout` gains an optional `goal_types` keyword. - **D-032** · PRP-00 was revised on the implementation branch while PRP-00 was being built (commits `5e37da4`, `fad5219`), adding the `YouthAllow` enum, `Exercise.youth_ok_by_band`, validator rule V14 and a `Progression` model renamed to `docs/exercise-principles.md` §5.1's field names. The implementation was rebuilt against the revision rather than the version it started from, so the branch carries both the new spec and code that matches it. Why: the protocol says the spec wins, and the tester and reviewer read the revised file. Consequence: `Progression` uses `rep_min`/`rep_max`/`regress_on` with `deload_pct` defaulting to 0.60, and seed YAML must not use `rep_low`/`rep_high`/`regress_triggers`/`bump_after_n_easy`, which no longer exist.
- **D-033** · V13 (`requires_anchor_unavailable`) runs for every profile, not only youth ones. Why: an overhead anchor is a hardware fact (`docs/exercise-principles.md` §1.7), not an age rule; an adult without a pull-up bar cannot do a dead hang either. Change: none expected.
- **D-034** · pre-commit is shipped as `.pre-commit-config.yaml` only; the git hooks are not installed on this workstation, so PRP-00 §10's `pre-commit run --all-files` box is not ticked. Why: build-orchestrator instruction. `make lint` (ruff check + ruff format --check) is the gate, and CI runs it. Change: `uv run pre-commit install`.
- **D-035** · Two `library/youth_rules.yaml` cells have no literal source in `docs/exercise-principles.md` §3.2. `u10.min_rest_s_loaded` is `60` where the table says *n/a*, because §3.9 types the field as a bare `int`; the value is inert, since `u10` allows no loaded row (`max_load_kg_*` are `0.0` and `allowed_load_types` excludes every implement). And `max_load_kg_per_hand` / `max_load_kg_per_implement` are widened to `float | None` so the adult band's *none* is representable; the load cap treats `None` as "not capped here" and `0.0` as a real cap of zero, never as absent. Change: give `min_rest_s_loaded` an `int | None` type if a band ever needs a true n/a.

- **D-036** · `make dev` and `.env.example` default to port **8090** (the compose host port from PRP-09), not 8000. Why: an unrelated process holds 127.0.0.1:8000 on JD's workstation, and one number everywhere is simpler. `cadence/config.py` keeps 8000 as the in-container default.

- **D-040** · `ActivityIn.garmin_category` is validated against the **full 47-name `garminconnect.exercises.CATEGORIES` list**, not the 26 names D-018 mentions. Why: that 26 was how many of the categories Cadence asked about exist in the library, not a whitelist to enforce; the library is the authority on what Garmin accepts, and rejecting the other 21 real names would 422 a legitimate payload. `UNKNOWN` is still rejected, because it genuinely is not in the catalog. Change: intersect with an explicit tuple in `vitalforge-weight/app.py`'s `GARMIN_EXERCISE_CATEGORIES` if Cadence ever needs a narrower set.
- **D-041** · The cross-person 409 is raised **before anything is stored**, so a rejected push leaves no row at all. Why: PRP-05 §5.4 forbids a silent downgrade to store-only, and that only holds if the request fails whole — storing the session and answering 409 would strand it at `garmin_status='pending'` while every retry 409s too, with no way for the caller to tell a stored session from a rejected one. Change: insert before the guard and return 409 with the row id, if Cadence ever wants the session kept on a rejected push. **Interaction with D-042:** because the guard runs before the dedup lookup, re-posting an already-stored `skipped` session with `push_to_garmin: true` and no `garmin_target` returns 409 rather than the 200 the dedup path would give — even though D-042 means that session would not have been pushed anyway. PRP-06 must therefore not flip `push_to_garmin` on a re-POST of a session first stored with it off; it decides once, at first post.
- **D-042** · `garmin_status='skipped'` is **not** retryable: a session first posted with `push_to_garmin: false` can never be pushed by a later POST of the same `session_id`. Why: contract §4.5 and PRP-05 §5.2 both name `('pending','failed')` as the retry set, mirroring `should_attempt_garmin_push`. Consequence for PRP-06: Cadence must decide `push_to_garmin` on the **first** post of a session, so a user toggling `push_son_to_garmin` on after a session is already stored will not back-fill it. Change: add `'skipped'` to `_RETRYABLE_GARMIN_STATUSES` in `vitalforge-weight/app.py`.
- **D-043** · `type_key="strength_training"` and `distance_km=0.0` are passed **explicitly at the app's call site** rather than defaulted inside `shared/garmin_client.push_activity`. Why: the test fake records only the kwargs the app actually passes, so defaults hidden in the wrapper would be untestable — and probe 3 (is `strength_training` a valid *activity* typeKey?) is the most likely thing to change. The string itself lives once, as `STRENGTH_ACTIVITY_TYPE_KEY`.
- **D-044** · `vitalforge-weight/app.py` is now **~1400 lines**, over the PRP protocol's 800-line hard max. Why: PRP-05 §5.1 puts the models, three routes and `_push_activity` in that file by name, and the file was already 809 lines before this PRP; splitting the service across a new sibling module means either an `importlib` dance (the directory is hyphenated and not a package) or moving request models into `shared/`, both larger and riskier changes than the PRP asked for. Mitigated by putting the exerciseSets payload builder and activity-id extraction in `shared/garmin_client.py` instead. Change: JD extracts a `shared/activity_api.py` if the file becomes unreviewable.
- **D-045** · `.venv-cadence/` needed **no** ignore entry: VitalForge's `.gitignore` already carries `.venv*/` (verified with `git check-ignore`). Nothing was added to `.git/info/exclude` or `.gitignore`.
- **D-046** · The "tests must never reach real Garmin" guard (PRP-05 §7 risk 3) is an **opt-in fixture** (`no_real_garmin_client`, selected per module with `pytestmark`), not a suite-wide autouse fixture. Why: autouse would add a check to all 770 tests, several hundred of which never touch a push path. Verified by mutation — removing the app-namespace patch in `conftest.py` turns the timezone module from 7 passing to 7 erroring.
- **D-047** · `TZ=""` is treated as unset and falls back to UTC with the same warning. Why: an empty string is what an unset variable looks like in a compose file that passes `TZ` through unconditionally, and `ZoneInfo("")` raises — which would otherwise turn a configuration gap into `garmin_status='failed'` on every single session.
- **D-037** · Five youth-gate bypasses found by the PRP-00 devil's-advocate review are closed, which adds four error codes to PRP-00 §5.1 and one field to `Exercise`. (a) The load cap now follows the **exercise's** `load_unit`, never the row's, and a loaded row under a unit the band table cannot cap (`total`, `bodyweight`) is `youth_load_uncappable` rather than uncapped; a row whose unit disagrees with its exercise is `load_unit_mismatch`. Before this, `load_unit: total` bought a nine-year-old 250 kg. (b) A youth profile carrying `age_band = adult` is coerced to `u10` with a `youth_band_coerced` warning, and `youth_allows(..., profile_kind="youth")` refuses to short-circuit on the adult band; the adult rule set exists in the YAML (D-029), so without this a youth profile ran zero youth checks. (c) V6 counts rows by the resolved exercise's new `Exercise.is_prelude`, not the row's flag, which a document set for itself; `WorkoutRow.is_prelude` survives as a display hint only. (d) V9 compares `max(declared, computed-from-rows)` against the cap, so a 33-minute session cannot declare one minute. (e) Assessment day is exempt from V6 and V9, and from the `max_effort` ban on `assessment_only` exercises only, so PRP-01 can seed the six-test battery (principles §3.4, §10.10). Also `profile_kind_mismatch` when a workout's `target_profile_kind` is neither `both` nor the caller's. Change: each rule is a named function in `cadence/validateur/youth_rules.py` with a regression test in `tests/test_schema_bypass.py`. **Second batch, from the Codex adversarial review:** (f) a `bodyweight_kg` that is not a finite positive real number - `nan`, an infinity, zero, a negative, a bool, a string - is `bodyweight_invalid` and is treated as *unknown* everywhere, because `nan` counted as known and every `nan > cap` comparison is False, so the percentage cap evaporated. (g) `youth_rep_ceiling` and `youth_rpe_exceeded` are now **errors**. `docs/exercise-principles.md` §3.10 labels them warnings, and this knowingly diverges: §3.10 describes the program engine, which silently caps and carries on, whereas this validator also gates `/api/import` and `/api/generate`, where nothing downstream applies a remedy - a `u10` row at 100 reps and effort 10 returned `ok is True`. `youth_band_coerced` is now the only warning, and acceptance test 21 pins `.ok` against it instead. (h) `frozen=True` is shallow, so DSL sequences are `tuple[...]`, mappings are `MappingProxyType` via a `FrozenMap` annotation, and `validate_exercise` / `validate_workout` re-validate a model instance from its own `model_dump()` rather than trusting it - `model_construct` builds one without validation. (i) Numerics are `StrictInt` / `StrictFloat` and booleans `StrictBool`, so YAML `true` is no longer `1` and `"12"` is no longer twelve; `StrictFloat` still accepts an int, so `load_kg: 12` stays legal. (j) A row prescribed in seconds is timed by its own number rather than the library's `est_seconds_per_set`, so one row of `seconds: 3600` cannot claim `estimated_minutes: 1`. (k) The assessment-day exemption from V6 and V9 is per row, not per session: only rows whose resolved exercise carries `assessment_only` are excluded, because `day_type` is document-declared and exempting the session let a 60-row `u10` workout declaring 120 minutes pass clean; principles §10.10 replaces those limits for the measured tests rather than removing them, and its own rows 1 and 2 are not `assessment_only`, so they keep counting.

- **D-048** · The Garmin push is claimed **inside** the `BEGIN IMMEDIATE` transaction via a new nullable `strength_sessions.garmin_claimed_at` (UTC ISO), not gated on `garmin_status` alone. Why: the winning request writes `'synced'` only after its synchronous Garmin call returns, long after its transaction committed, so a concurrent second request read `'pending'`, judged it retryable, and filed a **second** activity for one session — permanent, since this service has no delete path. `garmin_status` also could not distinguish "not yet attempted" from "attempted, outcome unrecorded"; the claim carries that distinction instead. A claim newer than `_GARMIN_CLAIM_TIMEOUT_SECONDS` (600 s) means in-flight: no push, dedup 200 with `garmin_status: "pending"` and no stale `garmin_error` echoed. An older claim is treated as a dead claimant and re-claimed with a WARNING, so a crash mid-push cannot strand a session unpushable forever — the deliberate trade is a possible duplicate after a crash over a guaranteed silent loss. The claim is cleared in `_record_activity_garmin_outcome`; if that write itself fails the claim is left to age out, which blocks an immediate duplicate, and the full outcome including `garmin_activity_id` is logged so an orphaned Garmin activity can be reconciled. The column is in the `CREATE TABLE` rather than an `_add_columns` shim because `strength_sessions` is new in this same unmerged branch, so no deployed database has the table at all. Change: narrow or widen the timeout constant in `vitalforge-weight/app.py`; a real lock table would be the next step if VitalForge ever runs more than one worker.

## PRP-01 — Library, seed content and program engine (2026-09-06)

- **D-050** · `profile` gains three columns beyond `docs/architecture.md` §3: `bodyweight_kg REAL NULL`, `has_overhead_anchor BOOLEAN NOT NULL DEFAULT 0` and `age_band TEXT NOT NULL DEFAULT 'u10'`. Why: the §3.3 percentage caps are uncomputable without a bodyweight, §1.7 anchor filtering needs the boolean (D-019), and the band is a denormalised cache of `age_band()` so a query can filter without recomputing. The cache is recomputed on every write, never read as the source of truth — `age_band(profile)` derives it from `kind` and `age_years` each time. Change: drop the cache column and call `age_band()` at every read site.
- **D-051** · The posture prelude is prepended to **every** session including `assessment-day`. Why: `docs/exercise-principles.md` §2 is categorical ("Runs first in every session for both profiles"); §10.10's numbered list is the measured block only, not the whole session. D-027 already assumed this for the youth banned-word check. Change: skip the prelude for `day_type == assessment` in `cadence/programme/materialise.py`.
- **D-052** · Inverse links are an **index on `LibraryBundle`** (`easier_than` / `harder_than`), never written back into `Exercise`. Why: `Exercise` is frozen and carries one `regression_of` and one `progression_of` slot, but §9's edges are many-to-one in four places — `push-up` is the harder successor of both `knee-push-up` and `incline-push-up-bench`, `plank` of both `dead-bug` and `bird-dog`, `dead-hang` of both `scap-pull-hang` and `db-floor-pullover`, and `inverted-row` would overwrite `bench-supported-db-row`'s declared `regr_of: db-bent-row`. Both declared directions collapse into one easier/harder graph: `x.regression_of = y` and `y.progression_of = x` both mean "x is easier than y". Seed documents stay verbatim. Change: none expected; PRP-07 reads the two dicts.
- **D-053** · `is_prelude: true` is set on the five posture-prelude movements (`cat-cow`, `open-book`, `wall-angel`, `glute-bridge`, `dead-bug`). Why: without it V6 counts the prelude against `max_exercises_per_session` and every youth session fails (5 training rows + 4 prelude rows > 5 at `u10`). Consequence: `glute-bridge` and `dead-bug` also appear as training rows in `son-lower-a`, and `wall-angel` on `assessment-day`, so those rows do not count toward the youth exercise cap either. That is a deliberate under-count of three low-load bodyweight movements; V9 (session length) still measures them, so an imported document cannot buy unlimited volume with them. Change: move the flag to `WorkoutRow` and re-open the self-exemption hole D-037(c) closed — do not.
- **D-054** · §10.10 says assessment rows 3–6 "carry `max_effort` and `assessment_only`", but PRP-00's `WorkoutRow` has no tag field and the validator reads tags off the **exercise** (D-037c/e). Tagging `push-up`, `plank` and `farmer-carry` `max_effort` at the library level would ban them for every youth band in `upper-b`, `son-upper-a` and `together-full-body`, where §10 prescribes them. So **no seed exercise carries `max_effort` or `assessment_only`** — which is also what §9's tags column says, verbatim. The battery still fits the youth caps without D-037(e)'s exemption: `wall-angel` is `is_prelude` (D-053) and `dead-hang` is filtered out with no overhead anchor, leaving four counted rows at `u10` against a cap of five. Change: add the two tags to the three exercises only if the seed ever needs the exemption, and accept the consequences for the other workouts.
- **D-055** · §10's load rules name no absolute starting weight for the ladder-rounded rows ("ladder-rounded, RPE 8 target"), and §5.7's "load from last block's week 3" has no answer in block one. Week-1 targets are therefore expressed as `pct_of_heaviest`, a fraction of the heaviest rung the household actually owns, so the seed adapts to any `weights_available` string instead of hard-coding this household's dumbbells. `relative_to` + `pct` keeps its own meaning (a fraction of another row's resolved load), and the two keys are deliberately spelled differently so neither silently does the other's job. Change: replace `pct_of_heaviest` with `kg` on a row once real week-3 history exists.
- **D-056** · `TemplateRow` gains three keys beyond PRP-01's list, all resolved at compile time and none reaching `WorkoutRow`: `anchor_alt` (§10.4's "if `has_overhead_anchor`, row 4 is replaced by `scap-pull-hang`"), `youth_skip` (§2's youth prelude variant drops `dead-bug`) and `assessment_id` (binds an assessment row to its `AssessmentSpec` so §7.4's per-band targets can be applied as data rather than by matching exercise ids in code). Why: each is a rule the principles state and the concrete model cannot express. Change: they are ordinary fields on this PRP's own `TemplateRow`.
- **D-057** · `rows_json` carries a `progression` key beyond the shape printed in PRP-01. Why: the PRP itself says the `Progression` document serves "the per-row mutable state copied into `rows_json` by `materialise_rows`, where PRP-07 rewrites the same field names" — the state has to live somewhere, and PRP-07 owns no other column. `rep_min` on that copy is the **template's week-1 value**, not the library default, which is what makes §6.2's P7 override and acceptance test 12 (`reps == rep_min` in week 4) the same number. `rep_max` is `rep_min + 4`, the top of the §6.2 week ladder. Change: move the state to its own column if `rows_json` grows unwieldy.
- **D-058** · The youth day-type map reuses templates: `upper_a` → `son-upper-a`, `lower_a` → `son-lower-a`, `mobility_carry` → `son-play-day`, `assessment` → `assessment-day`, and — with no §10 template of their own — `upper_b` → `son-upper-a` and `lower_full_b` → `together-full-body` (a `both` workout whose `day_type` already is `lower_full_b`). Why: a four-day youth week needs four resolvable day types and §10 ships three youth workouts; picking from the pool would make the choice non-deterministic. - **D-049** · A Garmin push whose outcome is genuinely unknowable records `garmin_status='unknown'`, a fifth status that is **never auto-retried and never auto-reclaimed** however old its claim. Two paths reach it: a transport error raised *after* the request may already have been sent (classified by exception class name across the MRO and `__cause__` chain, since garminconnect layers requests/urllib3/curl_cffi and which surfaces is a transport detail; a pre-send list — `ConnectTimeout`, auth failures, 429 — is checked first and wins, and everything before the HTTP call sits in its own `try` so our own JSON/`ZoneInfo` errors stay `failed`), and a push that succeeded but whose outcome write failed, which falls back to a minimal `unknown` write. Why: this service has no delete path, so a blind retry over a session Garmin may already hold creates a **permanent** duplicate. The asymmetry is deliberate — mis-calling a real failure `unknown` costs one lookup, mis-calling an ambiguous success `failed` costs a duplicate. An explicit re-POST **reconciles before pushing**: `get_activities_by_date` over the session's local date ±1 day (Garmin files by account-local date and the name is built from a local wall clock, so a near-midnight session lands on the neighbouring day), matching the exact `activity_name`. Found → `synced` with that id and `garmin_sets_status` left `not_attempted` (whether the sets call ever ran is not knowable from the lookup). Not found → push. **Lookup failed → stays `unknown`**, never collapsing into "not found", which is the mistake that duplicates. That name-collision residual is closed by a session marker: the activity title carries the last `_SESSION_MARKER_CHARS` (6) of the client-generated `session_id` as a suffix, so the D-015 forms become `Cadence — Lower A [6-a3f9]` and `Cadence (Son) — Lower A [6-a3f9]`. Without it, two sessions one person completed on one day under one label (a morning and an evening workout, or a redo) produce identical titles, and reconciling the second would adopt the **first** one's `activityId` — the second reading `synced` against an activity that is not it, its own push never happening. A suffix, not a prefix, so the human-meaningful part still leads where Garmin truncates long titles from the right; 6 characters because this is a disambiguator, not an identifier, and a 128-char `session_id` in a title would be unreadable. The name is composed once and used for both the push and the lookup, since two compositions that could drift would search for a title the push never sent. Change: `_AMBIGUOUS_TRANSPORT_ERRORS` / `_PRE_SEND_ERRORS` / `_SESSION_MARKER_CHARS` in `vitalforge-weight/app.py`.
